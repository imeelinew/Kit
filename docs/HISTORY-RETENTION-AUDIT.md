# 历史保留时长评估

评估日期：2026 年 10 月 7 日

结论：原实现覆盖基本的按时间清理，但缺少缩短时长的确认和多项一致性保障，本次已完成确认交互、定期维护、事务清理和文件删除恢复，剩余产品边界见文末

## 已确认的行为

- 提供 1 天、7 天、30 天、90 天、180 天、365 天和永久七档，默认 90 天，设置保存在本机
- 时长按固定的 24 小时天数计算，月份并不是日历月
- 使用最近一次外部复制的时间判断过期，再次复制相同内容会刷新时间，从 Kit 粘贴或复制历史项只更新使用时间，不延长保留期限
- 清理查询覆盖整个数据库，不受最近 1000 条内存窗口限制
- 所有历史类型和 Stack 内的记录都会过期，Stack 名称本身保留
- 数据库触发器负责同步删除文本和图片文字搜索索引，迟到的分类和识别结果不能重建已经删除的行
- 图片删除限于 Kit 图片目录中直接管理的普通 PNG，有目录、扩展名和符号链接检查，原始文件不属于这项清理范围

## 缺陷及处置

| 优先级 | 缺陷 | 影响 | 本次处置 |
| --- | --- | --- | --- |
| 高 | 下拉选择直接保存设置并执行删除，没有确认 | 从一年改为一天会立即永久删除超过一天的已有历史及图片，改回一年无法恢复 | 已接入用户批准的原生确认弹窗，确认前不改变设置或删除数据 |
| 中 | 图片路径查询与行删除分开执行，没有统一事务 | 无法对图片删除任务、历史行和关联状态提供整体提交保证 | 将图片删除任务、Stack 关联删除和历史行删除放进同一事务 |
| 中 | 清理没有删除 Stack 关联和内存映射 | 本次会话残留不存在的项目关联，重启前状态不一致 | 在事务内清理关联，提交后同步内存映射，保留空 Stack |
| 中 | 仅删除内存窗口以外的记录不更新修订号 | 分页搜索结果可能继续显示已删除记录 | 成功删除非驻留记录也发布修订号 |
| 中 | 清理只在启动、修改设置和新增不同内容时触发 | 常驻应用在没有新内容或只有重复内容时可无限保留过期历史 | 添加每小时维护任务，并在重复捕获时检查清理是否到期 |
| 中 | 清理开始时就更新时间，失败也会推迟下一次重试 | 数据库失败后，后续捕获可能一小时都不重试 | 仅成功提交后更新时间 |
| 中 | 图片删除使用不留状态的后台任务，并忽略文件删除错误 | 删除失败或提交后退出，会留下数据库已无记录的图片文件 | 新增持久化删除队列，分批后台删除，失败留待后续维护或重启重试 |
| 中 | 无效的底层时长没有防护 | 负值等异常输入可能扩大删除范围 | 非法输入拒绝清理，永久档显式跳过过期删除 |
| 中 | 删除失败没有反馈，设置已被提前保存 | 界面与实际执行结果不一致，之后重启仍可能按新时长删除 | 数据库提交成功后才保存设置，失败保留原策略并显示错误 |

## 已批准并实现的交互

维持现有下拉控件和页面布局，只调整缩短时长时的提交过程

1. 选择更短的时长时，先统计完整数据库中的受影响记录，不保存新设置、不删除数据
2. 显示原生确认弹窗，明确新时长、当前将删除的总条数、其中图片条数和 Stack 内条数，以及删除不可撤销
3. 提供「取消」和破坏性操作「删除并更改」按钮，取消或关闭弹窗时保留原设置
4. 用户确认后才应用新策略，数据库事务成功后才保存设置，失败恢复旧策略并显示错误
5. 延长时长、选择永久或缩短后不会删除任何现有记录时直接应用，只有实际删除数量大于零时才要求确认
6. 弹窗打开期间继续使用旧策略，确认时重新核对统计，若受影响数量已增加则更新确认内容，避免删除超过已展示范围的数据

完整历史统计、确认和提交接口均已接入正式界面，查询失败返回失败而不是零条，保留时长只能在成功提交后持久化，已按用户要求删除关于后续自动清理的额外文案

## 验证

新增独立的保留时长测试，所有数据均放在随机临时目录，不访问用户的真实历史

- 七档时长，过期边界，重复执行和异常输入
- 超过 1000 条内存窗口的统计、删除和修订通知
- 文本及图片文字搜索索引、Stack 关联和图片文件同步
- 数据库错误时回滚，后续捕获重试，撤销状态保留
- 文件删除失败后重启恢复，文件已经不存在时安全完成
- 外部路径、路径穿越、符号链接、目录和仍被其他历史行引用的图片保护
- 没有新增捕获时的定期清理
- 数据库不可用时的失败结果
- 确认前与取消后不改变持久化设置，确认后的提交与失败回滚
- 确认期间删除数量增加时重新要求确认，分别检查总条数、图片数和 Stack 内条数
- 原生界面验证取消后仍显示一年，数量增加后弹窗更新并重新确认

已有搜索、重复捕获、图片文字识别、图片搜索设置与列表撤销回归均已通过，macOS 应用构建成功

在本机用 50,000 条合成文本记录测量，完整历史统计约 7 毫秒，主线程事务删除约 248 毫秒，实际耗时取决于文本长度、索引、磁盘和 Stack 数量，这不是最坏情况上限

## 产品边界和剩余限制

- 正常过期清理仍是永久删除，没有批量撤销或回收站，这属于需要另行批准的产品设计
- Stack 目前是分组，不是永久收藏，若希望 Stack 内容永不过期，需要明确改变产品语义
- 每小时维护意味着正常清理允许约一小时的延迟，应用关闭或系统休眠时不能保证实时执行，启动时会补清理
- 已删除记录的时间跨度只能扩大后续保留范围，延长期限不会恢复已经删除的数据
- SQLite 删除释放可复用的数据库页，但不保证数据库文件立即缩小，也不是安全擦除承诺
- 旧版本已经留下且没有任何数据库记录的孤立图片，不会被新队列自动识别，避免扫描时误删正在保存的新图片
- 数据库批量删除仍在主线程执行，大量历史的删除和索引更新可能短暂阻塞，文件删除已移到后台，超大数据量的线程迁移需要独立评估
- 新增队列可恢复本次及之后的保留时长清理，手动清空历史和删除 Stack 的文件恢复机制不在这次修改范围内
